## 1. 结论

当前文档已经足够启动 MVP 的基础开发，尤其适合按“服务端接口 → 地图渲染 → 交互闭环 → 部署验证”的顺序推进。

但还不适合直接让 AI 一次性生成完整项目。原因是接口契约、运行环境、组件边界和测试方式仍有少量实现选择未定。推荐采用小任务、可运行、每步验收的方式开发。

就绪度：**约 75%**。

## 3. 开发前仍需补齐的决策

这些内容不一定要单独写成长文，但应在开始对应任务前确定：

1. **项目运行版本**
   - Node.js 版本。
   - 包管理器。
   - Next.js、React Flow、Tailwind 和动画库版本。
   - 本地启动命令和生产构建命令。

2. **知乎接口适配层**
   - 实际调用方式、请求头和响应字段映射。
   - 超时、重试和限流的具体秒数。
   - 直答和搜索接口的 mock 数据格式。
   - API 返回异常时的统一错误结构。

3. **地图数据契约**
   - `KnowledgeMap` 的完整 TypeScript 类型。
   - 前端节点数据如何转换为 React Flow node 和 edge。
   - SSE 事件的 JSON payload。
   - 缓存命中时是否仍通过 SSE 返回。

4. **本地进度规则**
   - localStorage key 名称。
   - 存储结构和版本字段。
   - 相同节点在不同地图中的 ID 是否隔离。
   - 用户清除进度的入口和行为。

5. **缓存和额度**
   - TTL 判断以服务端时间为准。
   - 并发请求合并的 key 和生命周期。
   - quota 更新是否需要原子操作。
   - 缓存写入失败是否影响用户看到的结果。

6. **测试与验收环境**
   - 外部 API 不可用时必须有 mock 模式。
   - 至少准备一个固定的完整地图 JSON。
   - 至少准备成功、空结果、超时、限流和非法 JSON 五种 fixture。
   - 需要明确桌面端目标浏览器和最小屏幕宽度。

## 4. 建议的 Vibe Coding 工作方式

每次只给 AI 一个可运行目标，并要求它：

1. 先读取相关文档和当前代码。
2. 只修改本任务涉及的文件。
3. 不添加未在范围内的功能。
4. 完成后运行 lint、类型检查或测试。
5. 汇报修改文件、验证命令和未解决问题。

推荐任务顺序：

1. 初始化 Next.js 项目和基础样式。
2. 定义所有领域类型、错误类型和 mock 数据。
3. 实现知乎客户端适配层，先支持 mock。
4. 实现话题归一化、缓存和额度保护。
5. 实现 `/api/outline`。
6. 实现 `/api/resources`。
7. 实现首页和预生成话题入口。
8. 实现静态地图和三层布局。
9. 接入 SSE 和节点逐个点亮。
10. 实现资源卫星圈、外链跳转和 localStorage 进度。
11. 实现一级下钻和面包屑。
12. 补齐降级状态、风险提示和部署配置。

## 5. 建议新增的最小开发约定

开始编码前，建议在仓库根目录补充：

- `README.md`：安装、环境变量、本地启动、构建和部署。
- `.env.example`：只列变量名，不放真实凭证。
- `docs/api-contract.md`：接口请求、响应、错误和 SSE 事件。
- `docs/test-fixtures.md`：mock 数据和异常场景。

如果希望减少文档数量，也可以将后两项合并到 `prd.md`，但接口契约最好保持独立，便于每次让 AI 只读取必要上下文。

## 6. 当前不应让 AI 自行决定的事项

- 不要自行增加登录、OAuth、数据库用户进度或第三方模型。
- 不要把知乎文章全文抓取到数据库。
- 不要把所有地图节点一次性阻塞到资源搜索完成后再渲染。
- 不要用模型主观评分替代知乎搜索相关性和社区互动数据。
- 不要在没有 mock 的情况下把真实知乎 API 作为唯一开发路径。
- 不要为了美化地图引入与主流程无关的复杂状态管理。

## 7. 最终判断

文档可以支持 vibe coding，但应采用“先补契约，再分任务实现”的方式。最先补齐 `README.md`、`.env.example` 和接口契约后，就可以稳定进入编码阶段；否则 AI 仍能开始工作，但很容易在 API 字段、SSE 行为、缓存边界和进度 key 上产生不一致实现。

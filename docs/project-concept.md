# 知径 · 项目构思文档

> 从一个话题，长出一张地图
>
> 知乎黑客松 2026 校园新锐季（`zhihu_hackathon_2026_p2`）参赛作品构思
> 撰写时间：2026-09-12 ｜ 提交窗口：2026-09-13 10:00 – 09-15 10:00

---

## 1. 一句话定位

输入任意想学的话题，知径把知乎社区里最被认可的学习资源，编排成一张可探索、可下钻的知识地图。

- **目标用户**：泛兴趣学习者（想搞懂一个领域，但不知道从哪读起、读什么）
- **核心价值**：把知乎碎片化的高质量内容，还原成有先后顺序的学习路径
- **组织逻辑**：认知难度递进 —— 入门 → 进阶 → 深入

## 2. 为什么值得做（评委视角的三个亮点）

**1）填的是知乎生态的真实空缺。** 知乎有大量高质量学习内容，但它们天生是碎片：一篇讲极限、一篇讲泰勒展开、一篇讲学习方法。搜索给你一个列表，没有任何产品告诉你"先读哪个、再读哪个"。知径不生产内容，只做编排，价值完全建立在社区已有内容之上。

**2）结构由 AI 编排，权重由社区投票决定。** 知识节点之间的依赖关系交给直答生成（LLM 擅长的事），而每个资源的重要性用赞数、评论数、作者认证等级这些硬数据算出来（LLM 不擅长的事）。圆圈越大 = 社区讨论越充分，不是模型的主观打分。这条分工是项目的技术叙事主轴。

**3）全链路只用知乎开放能力。** 实测直答 API（`https://developer.zhihu.com/v1/chat/completions`，模型 `zhida-fast-1p5`）是 OpenAI 兼容接口，能在约 7 秒内稳定输出结构化 JSON 大纲。因此大纲生成用直答、资源检索用知乎搜索，**不引入任何第三方 LLM**。

## 3. 用户流程

```
首页（8 张预生成话题卡片 + 搜索框）
  │
  ├─ 点卡片 → 秒开缓存地图
  └─ 输入话题 → 实时生成
                  │
        ① 直答生成大纲（约 7s）→ 骨架立即渲染，节点为灰色空心圈
                  │
        ② 各节点并发搜索知乎 → 资源到位后逐个"点亮"：圈上色、按权重放大
                  │
                  ▼
        完整地图（Heptabase 式白板，可平移 / 缩放 / 拖拽）
          ├─ 顶部：话题总览（这是什么 · 学完能干什么 · 大约多久）
          ├─ 点击知识点圈 → 原地展开 3 个文章卫星圈
          │     └─ 点卫星圈 → 新标签打开知乎原文（视为"已学"，节点标记完成）
          └─ 节点菜单「以此为中心展开」→ 递归生成子地图，面包屑返回
```

## 4. 视觉与交互规格

| 项 | 规格 |
|---|---|
| 整体风格 | 米白底（`#FAF9F5` 一类）+ 彩色卡片，参考 Heptabase 白板质感 |
| 画布 | React Flow：无限画布、滚轮缩放、空格拖拽平移、节点可拖动 |
| 布局 | 三层从左到右（入门 / 进阶 / 深入），层内纵向排开；用 dagre 自动布局后允许手动微调 |
| 层级配色 | 入门=柔绿、进阶=柔蓝、深入=柔紫；已学节点降饱和 + 勾选角标 |
| 节点大小 | 半径映射该知识点 top3 资源的权重之和（归一化到 40–90px） |
| 连线 | 主线（`main`）实线粗箭头；支线（`branch`）虚线细箭头 |
| 卫星圈 | 点击知识点后以扇形展开 3 个小圈，显示标题截断 + 赞数；再点收起 |
| 加载态 | 灰色空心圈 + 呼吸动画；点亮时轻微弹性放大 |
| 进度 | 顶部进度条「已浏览 4 / 11 个知识点」 |

## 5. 技术架构

```
Next.js（App Router）单仓单部署
  ├─ 前端  React + React Flow + Tailwind + Framer Motion（点亮动画）
  ├─ API Routes
  │    POST /api/outline    话题 → 直答 → 大纲 JSON（含每节点搜索词）
  │    POST /api/resources  单个节点搜索词 → 知乎搜索 → 排序 → top3
  │    GET  /api/map        读缓存地图（预生成话题秒开）
  │    GET  /api/auth/*     知乎 OAuth 授权 / 回调 / 会话
  │    POST /api/progress   已学节点同步（登录后）
  └─ 部署  腾讯云 CloudBase（Next.js 托管 + 云数据库）
           国内节点，调用 developer.zhihu.com 无跨境延迟风险
```

**为什么不用 Vercel**：海外节点访问 `developer.zhihu.com` 延迟与稳定性未经验证，而生成一张地图要串 1 次直答 + 11 次搜索，任何一跳抖动都会毁掉演示体验。

**凭证管理**：App Key / Access Secret / OAuth Token 只存在 CloudBase 环境变量中，全部知乎接口调用发生在服务端。App ID 可作为公开配置。凭证不进源码、不进前端响应、不进日志。

### 数据模型

```ts
type KnowledgeMap = {
  topic: string
  overview: { what: string; gain: string; duration: string }
  nodes: MapNode[]
  edges: { from: string; to: string; type: 'main' | 'branch' }[]
  generatedAt: number
}

type MapNode = {
  id: string
  title: string
  level: 1 | 2 | 3          // 入门 / 进阶 / 深入
  summary: string
  query: string             // 直答给出的知乎搜索词
  resources: Resource[]     // top3，可能为空
  weight: number            // resources 权重之和，决定圈大小
  state: 'pending' | 'ready' | 'empty'
}

type Resource = {
  title: string
  url: string
  author: string
  type: 'Article' | 'Answer'
  voteUpCount: number
  commentCount: number
  excerpt: string
  score: number
}
```

存储：CloudBase 云数据库三个集合 —— `maps`（话题地图缓存，key 为归一化话题名）、`progress`（`userId` → 已学节点 id 列表）、`quota`（当日调用计数，用于额度保护）。未登录用户的进度存 localStorage。

### 数据流水线

1. **归一化话题**：trim、去标点、统一大小写，作为缓存 key。命中缓存（TTL 24h）直接返回。
2. **生成大纲**：调直答，要求输出 10–12 个节点、三层分布、主线 + 支线边、每节点一个知乎搜索词。非学习类话题要求返回 `{"error":"not_learnable"}`。输出解析失败自动重试 1 次。
3. **并发检索**：每个节点一次 `zhihu_search`（`count=10`），并发度限制 5，避免瞬时打爆额度。
4. **排序取 top3**：见下方公式。
5. **写缓存 + 流式返回**：大纲先通过 SSE 推给前端渲染骨架，每个节点资源就位后推一条增量事件。

### 权重公式

```
base    = log(1 + voteUpCount) + 0.5 · log(1 + commentCount) + 0.3 · authorityLevel
type    = Article ? 1.2 : 1.0
classic = voteUpCount ≥ 500 ? 1 + 0.03 · min(内容年龄年数, 5) : 1.0
score   = base × type × classic
```

设计意图：取对数抑制头部长尾差异；**不做时间衰减**，反而给"高赞老文章"一点经典加成（符合"更信任经过时间检验的内容"的取向）；Article 优先体现系统性偏好。知乎自带的 `RankingScore` 作为同分时的兜底排序键。

排序策略保留一个开关：若纯公式效果不佳（噪音多、书单混入），切换到 **公式初筛 10 条 → 直答精选 3 条并生成推荐理由**，代价是每张图多约 5–8 秒（可与点亮动画并行，用户无感）。书单 / 资源推荐类内容不丢弃，统一挂到一个独立的「资源推荐」节点。

## 6. 知乎能力使用清单

| 能力 | 用途 | 额度（当前账号） |
|---|---|---|
| 直答 `zhida_openai` | 生成学习大纲、话题总览、（可选）资源精选与推荐理由 | 5000 / 天 |
| 知乎搜索 `zhihu_search` | 按节点搜索词检索学习资源，取赞数 / 评论数 / 认证等级 | 5000 / 天 |
| OAuth 登录 | 用户身份，跨设备同步"已学"进度 | — |

一张地图的实时生成成本：1 次直答 + 11 次搜索 ≈ 12 次调用，日额度足够支撑数百次生成。缓存与请求去重在应用层完成。

## 7. 降级与兜底（全部由前端呈现真实状态）

| 场景 | 表现 |
|---|---|
| 某节点搜索为空 | 虚线灰圈 + "社区暂无优质资料"，点击跳知乎站内搜索该关键词 |
| 大纲生成失败 / 非 JSON | 自动重试 1 次；仍失败提示"这个话题暂时无法生成地图，试试更具体的说法" |
| 输入非学习类话题 | 直答返回 `not_learnable`，前端给友好提示并推荐首页示例话题 |
| 搜索接口报错 | 该节点标记为可重试状态，提供单节点"重试"按钮，不让整张图失败 |
| 额度耗尽 | 明确显示"今日实时生成额度已用完"，仍可浏览全部缓存话题 |
| 未拿到 OAuth 凭证 | 隐藏登录入口，进度走 localStorage，核心体验完整不受影响 |

**OAuth 风险预案**：官方文档说明 App ID / App Key 通过赛事页面「创建项目」获取，而创建项目入口在提交窗口开放（9/13 10:00）后才可用，凭证领取时机尚未核实。因此登录必须是可插拔的增强项：未登录路径为默认路径，全流程可用。

## 8. 演示准备

预生成并缓存 8 个话题，覆盖不同领域以证明"任意话题"能力：

微积分 · 量子力学 · Python 入门 · 投资理财 · 认知心理学 · 摄影 · 咖啡 · 日本历史

演示动线：首页点「微积分」秒开完整地图（展示视觉与结构）→ 点节点展开卫星圈 → 跳转知乎原文，回来看到节点变已学 → 对「泰勒级数」做一次下钻 → 最后现场输入一个评委给的新话题，走完整实时生成，用骨架先出 + 逐点点亮把 20 秒变成看得见的过程。

## 10. 范围边界

**做**：话题输入、地图生成与可视化、资源跳转、递归下钻、已学进度、降级提示、8 个缓存话题。

**不做**（写进产品说明的路线图，不写进代码）：节点编辑与自由拖拉建图、笔记与批注、多地图管理与双链、协作、移动端专门适配（保证不崩，但按桌面优化）、从收藏夹反向生成地图。

Heptabase 和 Litmaps 是重型产品，两天只够做透"输入话题 → 得到一张能用的地图"这一条主线。任何让这条主线变慢或变脆的功能都后置。

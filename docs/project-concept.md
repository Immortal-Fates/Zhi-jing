# 知径 · 项目构思文档

> 从一个话题，长出一张地图
>
> 知乎黑客松 2026 校园新锐季（`zhihu_hackathon_2026_p2`）参赛作品构思
> 撰写时间：2026-09-12 ｜ 提交窗口：2026-09-13 10:00 – 09-15 10:00

## 1. 一句话定位

输入任意想学的话题，知径把知乎社区里相关且具有较高社区互动度的学习资源，编排成一张可探索、可下钻的知识地图。

- **目标用户**：泛兴趣学习者（想搞懂一个领域，但不知道从哪读起、读什么）
- **核心价值**：把知乎碎片化的高质量内容，还原成有先后顺序的学习路径
- **组织逻辑**：认知难度递进 —— 入门 → 进阶 → 深入

## 2. 为什么值得做（评委视角的三个亮点）

**1）填的是知乎生态的真实空缺。** 知乎有大量高质量学习内容，但它们天生是碎片：一篇讲极限、一篇讲泰勒展开、一篇讲学习方法。搜索给你一个列表，没有任何产品告诉你"先读哪个、再读哪个"。知径不生产内容，只做编排，价值完全建立在社区已有内容之上。

**2）结构由 AI 编排，权重由社区投票决定。** 知识节点之间的依赖关系交给直答生成（LLM 擅长的事），而每个资源的重要性用赞数、评论数、作者认证等级这些硬数据算出来（LLM 不擅长的事）。圆圈越大 = 社区讨论越充分，不是模型的主观打分。这条分工是项目的技术叙事主轴。

**3）全链路只用知乎开放能力。** 直答 API（`https://developer.zhihu.com/v1/chat/completions`，模型 `zhida-fast-1p5`）提供 OpenAI 兼容的对话接口。因此大纲生成用直答、资源检索用知乎搜索，**不引入任何第三方 LLM**。服务端会对直答结果进行 JSON 清洗和结构校验，并通过重试与降级保证地图可用。

## 3. 用户流程

```
首页（3 张预生成话题卡片 + 搜索框）
  │
  ├─ 点卡片 → 秒开缓存地图
  └─ 输入话题 → 实时生成
                  │
        ① 直答生成大纲（约 7s）→ 骨架立即渲染，节点为灰色空心圈
                  │
        ② 各节点并发搜索知乎 → 资源到位后逐个"点亮"：圈上色、按权重放大
                  │
                  ▼
        完整地图（Heptabase 式白板，可平移 / 缩放 / 拖拽）
          ├─ 顶部：话题总览（这是什么 · 学完能干什么 · 大约多久）
          ├─ 点击知识点圈 → 原地展开 3 个文章卫星圈
          │     └─ 点卫星圈 → 新标签打开知乎原文（视为"已学"，节点标记完成）
          └─ 节点菜单「以此为中心展开」→ 最多生成一层子地图，面包屑返回
```

## 4. 视觉与交互规格

| 项 | 规格 |
|---|---|
| 整体风格 | 米白底（`#FAF9F5` 一类）+ 彩色卡片，参考 Heptabase 白板质感 |
| 画布 | React Flow：无限画布、滚轮缩放、空格拖拽平移、节点可拖动 |
| 布局 | 三层从左到右（入门 / 进阶 / 深入），层内纵向排开；用 dagre 自动布局后允许手动微调 |
| 层级配色 | 入门=柔绿、进阶=柔蓝、深入=柔紫；已学节点降饱和 + 勾选角标 |
| 节点大小 | 半径映射该知识点 top3 资源的权重之和（归一化到 40–90px） |
| 连线 | 主线（`main`）实线粗箭头；支线（`branch`）虚线细箭头 |
| 卫星圈 | 点击知识点后以扇形展开 3 个小圈，显示标题截断 + 赞数；再点收起 |
| 加载态 | 灰色空心圈 + 呼吸动画；点亮时轻微弹性放大 |
| 进度 | 顶部进度条「已浏览 4 / 11 个知识点」 |

## 5. 技术架构

```
Next.js（App Router）单仓单部署
  ├─ 前端  React + React Flow + Tailwind + Framer Motion（点亮动画）
  ├─ API Routes
  │    POST /api/outline    话题 → 直答 → 清洗校验后的大纲 JSON（含每节点搜索词）
  │    POST /api/resources  单个节点搜索词 → 知乎搜索 → 排序 → top3
  │    GET  /api/map        读缓存地图（预生成话题秒开）
  └─ 部署  腾讯云 CloudBase（Next.js 托管 + 云数据库）
           优先选择国内节点，并通过真实部署环境实测 developer.zhihu.com 的延迟与稳定性
```

**为什么暂不用 Vercel**：Vercel 的部署地域与 `developer.zhihu.com` 之间的延迟和稳定性尚未经过本项目真实环境验证；由于生成一张地图要串 1 次直答 + 多次搜索，任何一跳抖动都可能影响演示体验，最终以 CloudBase 与 Vercel 的实际测试结果为准。

**凭证管理**：App Key / Access Secret 只存在 CloudBase 环境变量中，全部知乎接口调用发生在服务端。App ID 可作为公开配置。凭证不进源码、不进前端响应、不进日志。

### 数据模型

```ts
type KnowledgeMap = {
  topic: string
  overview: { what: string; gain: string; duration: string }
  nodes: MapNode[]
  edges: { from: string; to: string; type: 'main' | 'branch' }[]
  generatedAt: number
}

type MapNode = {
  id: string
  title: string
  level: 1 | 2 | 3          // 入门 / 进阶 / 深入
  summary: string
  query: string             // 直答给出的知乎搜索词
  resources: Resource[]     // top3，可能为空
  weight: number            // resources 权重之和，决定圈大小
  state: 'pending' | 'ready' | 'empty' | 'error' | 'retrying'
  errorCode?: 'timeout' | 'rate_limited' | 'unauthorized' | 'provider_error'
}

type Resource = {
  title: string
  url: string
  contentId: string
  contentType: string
  author: string
  authorBadge?: string
  authorityLevel?: string
  rankingScore?: number
  voteUpCount: number
  commentCount: number
  excerpt: string
  editTime: number
  score: number
}
```

存储：CloudBase 云数据库两个集合 —— `maps`（话题地图缓存，key 为归一化话题名）、`quota`（当日调用计数，用于额度保护）。已学进度只存浏览器 localStorage，不做账号同步。

**内容展示与合规边界**：资源卡片展示知乎开放 API 返回的标题、摘要、作者、互动数据和原文链接，并明确标注“来源：知乎”；不额外抓取或长期保存文章全文，实际使用遵循知乎平台的授权与使用要求。大纲、学习顺序和预计用时属于 AI 生成的参考信息，不冒充原作者观点。对于金融、医疗、法律等具有较强时效性或专业风险的话题，页面提示相关内容不替代专业意见，用户应以官方信息和专业人士意见为准。

### 数据流水线

1. **归一化话题**：trim、去标点、统一大小写，作为缓存 key。命中缓存（TTL 24h）直接返回。
2. **生成大纲**：调直答，要求输出 6–10 个节点、三层分布、主线 + 支线边、每节点一个知乎搜索词。非学习类话题要求返回 `{"error":"not_learnable"}`。服务端先清洗模型输出，再校验 JSON 结构、节点数量、ID 唯一性、层级、搜索词和边的合法性；解析或校验失败自动重试 1 次，仍失败时保留可用节点并采用确定性布局，避免整张地图失败。
3. **并发检索**：每个节点一次 `zhihu_search`（`count=10`），并发度限制 5，避免瞬时打爆额度。
4. **排序取 top3**：先保留知乎搜索提供的相关性排序，并过滤明显不相关、广告、纯书单或资源汇总内容；再在候选集中综合考虑搜索名次、`RankingScore`、赞同数、评论数和可验证的权威等级。知乎搜索负责相关性，社区互动数据负责资源的优先展示顺序，最后取 top3。
5. **写缓存 + 流式返回**：大纲先通过 SSE 推给前端渲染骨架，每个节点资源就位后推一条增量事件。

### 权重公式

```
engagement = log(1 + voteUpCount)
            + 0.5 · log(1 + commentCount)
            + authorityWeight

normalizedEngagement = 在当前候选集内归一化后的 engagement
score = 0.6 · normalizedRankingScore
      + 0.4 · normalizedEngagement
```

设计意图：知乎搜索负责保证候选内容与知识节点的相关性，社区互动数据负责体现内容的讨论程度；对数函数抑制头部长尾差异。`normalizedRankingScore` 和 `normalizedEngagement` 均在当前节点的候选集内归一化，避免不同查询之间的原始分数直接比较。`authorityLevel` 为字符串，只有在已建立明确映射时才计入 `authorityWeight`，未知等级按 0 处理。`RankingScore` 作为相关性信号参与排序，而不是只在同分时兜底。Article 不再统一设置固定加成，老内容不直接增加排序分；满足高赞且发布时间较早条件的内容可展示「经典内容」标签。书单 / 资源推荐类内容默认标记为资源汇总，必要时放入独立的「资源推荐」区域，不额外调用直答精选。

## 6. 知乎能力使用清单

| 能力 | 用途 | 额度（当前账号） |
|---|---|---|
| 直答 `zhida_openai` | 生成学习大纲、话题总览、（可选）资源精选与推荐理由 | 5000 / 天 |
| 知乎搜索 `zhihu_search` | 按节点搜索词检索学习资源，取赞数 / 评论数 / 认证等级 | 5000 / 天 |

一张地图的实时生成成本：1 次直答 + 11 次搜索 ≈ 12 次调用，日额度足够支撑数百次生成。缓存与请求去重在应用层完成。

## 7. 降级与兜底（全部由前端呈现真实状态）

| 场景 | 表现 |
|---|---|
| 某节点搜索为空 | 虚线灰圈 + "社区暂无优质资料"，点击跳知乎站内搜索该关键词 |
| 大纲生成失败 / 非 JSON | 自动重试 1 次；仍失败提示"这个话题暂时无法生成地图，试试更具体的说法" |
| 输入非学习类话题 | 直答返回 `not_learnable`，前端给友好提示并推荐首页示例话题 |
| 搜索接口报错 | 该节点标记为可重试状态，提供单节点"重试"按钮，不让整张图失败 |
| 额度耗尽 | 明确显示"今日实时生成额度已用完"，仍可浏览全部缓存话题 |

## 8. 演示准备

首版预生成并缓存 3 个话题，优先覆盖不同类型且学习层次清晰的场景，以保证演示质量：

微积分 · Python 入门 · 摄影

其他话题仍支持通过搜索框实时生成，不纳入首版预生成地图的质量承诺；后续版本再扩充预生成话题。

演示动线：首页点「微积分」秒开完整地图（展示视觉与结构）→ 点节点展开卫星圈 → 跳转知乎原文，回来看到节点变已学 → 对「泰勒级数」做一次一级下钻 → 最后现场输入一个评委给的新话题，走完整实时生成，用骨架先出 + 逐点点亮把等待时间变成看得见的过程。

## 10. 范围边界

**做**：话题输入、地图生成与可视化、资源跳转、一级下钻、已学进度、降级提示、3 个首版缓存话题。

**不做**（写进产品说明的路线图，不写进代码）：节点编辑与自由拖拉建图、笔记与批注、多地图管理与双链、协作、移动端专门适配（保证不崩，但按桌面优化）、从收藏夹反向生成地图。

Heptabase 和 Litmaps 是重型产品，两天只够做透"输入话题 → 得到一张能用的地图"这一条主线。任何让这条主线变慢或变脆的功能都后置。
